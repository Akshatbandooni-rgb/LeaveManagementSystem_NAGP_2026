01

Communication Patterns

This system uses two distinct communication patterns, each chosen for specific reasons based on whether the caller needs an immediate answer and whether failure of the downstream operation should affect the caller's outcome.

Synchronous · Request-Response
HTTP via API Gateway
The caller sends a request and waits for a response before proceeding. The response directly determines the outcome returned to the client. All external client traffic enters through the API Gateway only — no client ever speaks directly to a business service. The Gateway validates JWT, enriches headers, applies the circuit breaker, and proxies to the correct downstream service discovered via Consul.
Used when: The client needs an immediate answer. Examples: login (client needs a token now), apply leave (client needs to know if it succeeded or failed), approve leave (manager needs confirmation). Any operation where the result is returned to the user in real time.
Asynchronous · Event-Driven
RabbitMQ Message Broker
The publisher emits an event to RabbitMQ and immediately continues — it does not wait for any consumer to process the message. The consumer processes the event independently and at its own pace. If the consumer is temporarily down, RabbitMQ holds the message in a durable queue until the consumer recovers. The publisher's operation succeeds regardless of consumer availability.
Used when: The result of the side-effect must not block or endanger the main operation. Examples: sending notifications (if notification logging fails, the leave approval must still succeed), initializing leave balances (if Leave Service is slow, User Service must not fail user creation).

The guiding principle for the pattern choice is: if a downstream failure should roll back or fail the current operation, use synchronous HTTP. If a downstream failure should have zero effect on the current operation, use async RabbitMQ.

Asynchronous Event Communication

RabbitMQ is configured with two topic exchanges, both declared durable. All queues are declared durable and messages are published with persistent: true, meaning messages survive a RabbitMQ restart. Consumers use manual acknowledgement — a message is only removed from the queue after the consumer explicitly acks it, preventing message loss if the consumer crashes mid-processing.

TriggerNew EMPLOYEE user saved in User Service. MANAGER creation does not publish this event.

On FailureNack with requeue:false. Message goes to dead-letter queue. Balance not initialized — employee gets 404 on first balance request.

RabbitMQ reliability configuration: All exchanges are declared with durable: true. All queues are declared with durable: true. All messages are published with persistent: true. This three-layer durability means messages survive a RabbitMQ process restart. The amqp-connection-manager library handles automatic reconnection if the connection drops — critical for Docker startup ordering where RabbitMQ may not be fully ready when services first attempt to connect.

04

Service Discovery via Consul

Consul eliminates hardcoded service addresses. Instead of the API Gateway knowing that Leave Service lives at http://leave-service:3002 at compile time, it queries Consul at request time for the current healthy address. This means services can be restarted, moved, or scaled without changing Gateway configuration.

◈ Registration
Each service calls Consul Agent API on startup after its HTTP server is listening.
Registration payload: name, id, address, port, check.http
Health check: Consul polls GET /health every 10 seconds
Deregisters after 30 seconds of critical (failing) health checks
On SIGTERM: service calls deregisterService() before shutdown
◈ Discovery
Gateway calls GET /v1/health/service/{name}?passing=true before each proxied request
?passing=true ensures only healthy instances are returned — unhealthy services are automatically excluded
Gateway takes the first result: instance.Service.Address + ':' + instance.Service.Port
If Consul returns empty array → AppError 503 Service Unavailable
◈ Fallback Strategy
If Consul itself is unavailable, the Gateway falls back to a hardcoded address map:
user-service → localhost:3001
leave-service → localhost:3002
Inside Docker: uses Docker service names as hostnames. Fallback is logged at WARN level.
This prevents a Consul outage from taking down the entire system immediately.
05

Circuit Breaker Pattern

The API Gateway wraps every downstream HTTP call in an Opossum circuit breaker, one per downstream service. Without a circuit breaker, a slow or unresponsive Leave Service would cause every Gateway request to hang for the full timeout duration, exhausting available connections and cascading the failure. The circuit breaker detects degradation early and fast-fails subsequent requests, protecting the Gateway and returning clear error responses to clients.

Downstream is unhealthy. All requests instantly return 503 without touching the downstream service. Stays open for 30 seconds then transitions to HALF-OPEN.

Trial mode. One test request is allowed through. If it succeeds, circuit closes. If it fails, circuit opens again for another 30 seconds.

The circuit state for each downstream service is exposed in the Gateway's GET /health response: { "circuits": { "leave-service": "closed", "user-service": "open" } }. This makes the circuit state observable during the demo without needing to look at logs. The fallback response when the circuit is open is: { "error": "leave-service is temporarily unavailable. Please retry after 30 seconds", "correlationId": "..." }

Correlation ID — Request Tracing Across Services

A Correlation ID is a UUID generated once per request at the API Gateway and carried through every service that request touches — including across async RabbitMQ event boundaries. It appears in every single log line, enabling you to reconstruct the complete story of any request by grepping for one value across all service logs. It is also returned in every HTTP error response body so clients can report it.

CLIENT
Sends request. May optionally include X-Correlation-Id header if the client has its own tracing system.
→ PATCH /leaves/abc/approve
X-Correlation-Id: (optional)
API GATEWAY
Generates UUID if header absent. Attaches to req.correlationId. Sets on response header. Forwards as X-Correlation-Id to downstream.
{ "service":"api-gateway",
  "level":"info",
  "correlationId":"req-7f3a9b",
  "msg":"Proxying to leave-service" }
LEAVE SERVICE
correlationId middleware reads X-Correlation-Id header. Attaches to req.correlationId. Every logger call in this request includes it. Passed into service function as input parameter.
{ "service":"leave-service",
  "correlationId":"req-7f3a9b",
  "msg":"Approving leave abc",
  "leaveId":"abc" }
{ "service":"leave-service",
  "correlationId":"req-7f3a9b",
  "msg":"Balance deducted" }
RABBITMQ EVENT
Leave Service embeds correlationId in the event payload before publishing. This bridges the async boundary — the ID travels inside the message itself.
{ "eventType":"leave.approved",
  "employeeId":"emp-001",
  "correlationId":"req-7f3a9b" }
NOTIFICATION SVC
Consumer reads event.correlationId from the parsed message. Logs notification with the same ID — connecting the async log entry back to the original HTTP request.
{ "service":"notification-service",
  "correlationId":"req-7f3a9b",
  "msg":"NOTIFICATION | Leave Approved
  | Employee: emp-001" }

To find all logs for one request: docker-compose logs | grep req-7f3a9b. This returns every log line from every service — Gateway, Leave Service, and Notification Service — in one output, giving the complete request timeline. The correlationId also appears in all error response bodies, so when a user reports an error, they include it and you search immediately.

07

Internal Header Contract

The API Gateway and downstream services communicate through a defined set of internal headers. The Gateway strips the raw JWT and replaces it with decoded, trusted context. Services must never accept the raw JWT — they trust only these headers, and only when the internal secret is present. This prevents any client from bypassing the Gateway and calling services directly with a forged identity.

Header Set By Read By Value Purpose
Authorization Client API Gateway only Bearer <jwt> Raw JWT token. Gateway validates and then strips this header before forwarding. Services never see it.
X-User-Id API Gateway All services e.g. emp-001 The authenticated user's ID, extracted from the validated JWT payload. Services set req.user.userId from this.
X-User-Role API Gateway All services EMPLOYEE or MANAGER The authenticated user's role. Used by requireRole middleware in each service.
X-Internal-Secret API Gateway All services Shared secret string Proves the request came through the Gateway. Services reject any request where this header is absent or wrong. Prevents Gateway bypass.
X-Correlation-Id API Gateway (generates or passes through) All services, RabbitMQ event payloads UUID v4 Request-scoped trace ID. Present in every log line and every error response. Embedded in async event payloads to bridge async boundaries.

For public endpoints (POST /auth/login, GET /health), the Gateway forwards X-Correlation-Id only. It does not add X-User-Id, X-User-Role, or X-Internal-Secret because no JWT was validated. The User Service's login route does not apply the internalAuth middleware — it is mounted publicly with no auth requirements.

08

Design Assumptions

The following assumptions were made during design. Each is documented with its rationale and the impact it has on the system — whether it is an MVP trade-off, a deliberate design decision, or a known limitation.

A1
In-Memory Storage is Acceptable for MVP
All data — users, leave requests, balances — is stored in Node.js Map objects. Data is lost on service restart. This is explicitly permitted by the assignment specification which states "In-memory collections or mock data stores" as a valid MVP approach.
MVP Trade-off
A2
managerId is Provided by the Client on Leave Application
When an employee applies for leave, they provide the managerId in the request body. The system validates it is a valid UUID but does not verify that the provided ID actually belongs to a manager in the user store. In production, the backend would look up the employee's assigned manager automatically from the employee record, preventing employees from routing their request to an arbitrary manager.
Production Gap
A3
numberOfDays is Client-Provided, Not Calculated
The numberOfDays field is sent by the client and trusted as-is. The system does not calculate it from startDate and endDate, nor does it validate consistency between the three values. A client could send startDate: 2026-09-01, endDate: 2026-09-03, numberOfDays: 10 and the system would accept it. In production, numberOfDays would be calculated server-side and the client value ignored.
Production Gap
A4
JWT Tokens Are Not Revocable
Once a JWT is issued, it is valid until its 8-hour expiry regardless of what happens — user deleted, role changed, password reset. There is no token blacklist. Implementing revocation requires a shared store (Redis) accessible by the Gateway. This is an intentional MVP simplification — the assignment does not require token revocation.
Security Trade-off
A5
Balance Initialization Has a Small Race Window
After a new employee is created, the user.created RabbitMQ event is published asynchronously. There is a brief window (milliseconds to seconds depending on consumer lag) where the employee exists but their balance has not yet been initialized. If the employee calls GET /balances/my-balance in this window, they receive a 404. In production, this would be handled by either synchronous balance initialization or a retry mechanism on the client.
Known Race Condition
A6
Notifications Are Log-Only — No Real Delivery
The assignment explicitly states no real email or SMS integration. The Notification Service consumes events and writes structured log entries using Pino. These logs are the "notifications." In production, the consumer would call an email provider (SendGrid, SES) or SMS gateway.
MVP Scope
A7
All Dates Are Treated as UTC Strings
Dates are stored and compared as YYYY-MM-DD strings. No timezone conversion is applied. "Today" for past-date validation is computed as new Date().toISOString().split('T')[0] — UTC date of the server. An employee in a timezone ahead of UTC could theoretically request a leave starting "tomorrow" in their timezone but "today" in UTC, receiving a 400 error. This is acceptable for MVP.
Design Decision
A8
Single Instance Per Service — No Horizontal Scaling
Each service runs as a single Docker container. The in-memory Map stores live in the Node.js process heap. If two instances of Leave Service ran, they would each have separate Maps and would have inconsistent state — approving a leave on instance A would not update the balance on instance B. Horizontal scaling requires shared storage (database or Redis). This is an intentional MVP constraint.
MVP Scope
A9
Balance Deduction is Synchronous to Prevent Race Conditions
The deductBalance() function in the balance repository is deliberately fully synchronous — no await between reading the balance and writing the deducted value. Node.js processes one callback at a time, so a synchronous read-check-deduct-write block cannot be interleaved by another concurrent operation. If await were added between the read and write, two concurrent approval requests could both read a sufficient balance before either writes, causing double-deduction.
Design Decision
A10
user.created Event Initialization is Idempotent
RabbitMQ guarantees at-least-once delivery — a message may be delivered more than once in rare failure scenarios. The initializeBalance() function checks if a balance already exists for the userId before creating one. If it does, it returns the existing balance without modification. This makes the consumer idempotent — processing the same user.created event twice produces the correct result.
Design Decision
