Authentication

The authentication service is the entry point for all users. A successful login returns a JWT token that must be included as a Bearer token in all subsequent protected requests via the Authorization header.

POST /auth/login Authenticate a user and receive a JWT token ▶
Overview
Validates user credentials and returns a signed JWT token along with the user's role. The token must be stored client-side and sent in all subsequent authenticated requests.
Authentication
Public No token required
Authorization
None — open endpoint accessible by all users.
Request Headers
HeaderRequiredDescription
Content-TypeYesMust be application/json
Request Body
{
  "email": "alice@company.com", // string · required · valid email format
  "password": "password123"         // string · required · min 6 characters
}
FieldTypeRequiredValidation
emailstringYesMust be a valid email address
passwordstringYesMinimum 6 characters
Success Response — 200 OK
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "role": "EMPLOYEE" // "EMPLOYEE" | "MANAGER"
}
Error Responses
StatusWhen It OccursResponse Body
400 email or password field is missing from the request body { "error": "Validation failed", "details": [...] }
401 Email not found or password does not match { "error": "Invalid credentials" }

User Management

03

Leave Balance

Each employee has three leave buckets: CASUAL (12 days), SICK (10 days), and PRIVILEGE (15 days). Balances are auto-initialized via RabbitMQ when a user is created and are decremented when a leave request is approved. This endpoint is restricted to the EMPLOYEE role.

GET /balances/my-balance Retrieve the authenticated employee's current leave balances ▶
Overview
Returns the remaining leave day counts for all three leave types for the currently authenticated employee. The identity of the employee is derived entirely from the JWT — no path parameter is required.
Authentication
Requires Employee Token
Authorization
EMPLOYEE role only. Manager tokens are rejected with 403. An employee can only view their own balance.
Request Headers
HeaderRequiredDescription
AuthorizationYesBearer <token> — must be an Employee JWT
Success Response — 200 OK
{
  "CASUAL": 9, // integer · remaining casual leave days
  "SICK": 10, // integer · remaining sick leave days
  "PRIVILEGE": 15    // integer · remaining privilege leave days
}
Error Responses
StatusWhen It OccursResponse Body
401No token or invalid/expired token provided{ "error": "Authorization token required" }
403Token belongs to a MANAGER role user{ "error": "Insufficient permissions" }

Apply Leave

Employees use this endpoint to submit new leave requests. The system validates date ranges, checks for overlapping requests, and verifies sufficient leave balance before creating the request in PENDING status awaiting manager action.

POST /leaves Submit a new leave request ▶
Overview
Creates a new leave request with status PENDING. The employee's identity is extracted from their JWT. The system checks that dates are in the future, the range is valid, there are no date overlaps with existing requests, and the employee has sufficient balance for the requested leave type.
Authentication
Requires Employee Token
Authorization
EMPLOYEE role only. Managers cannot submit leave requests. Employee ID is always inferred from the JWT, not from the request body.
Request Headers
HeaderRequiredDescription
AuthorizationYesBearer <token> — must be an Employee JWT
Content-TypeYesMust be application/json
Request Body
{
  "leaveType": "CASUAL", // string · required · "CASUAL" | "SICK" | "PRIVILEGE"
  "startDate": "2026-09-01", // string · required · ISO 8601 date · must not be in the past
  "endDate": "2026-09-03", // string · required · ISO 8601 date · must be >= startDate
  "numberOfDays": 3, // integer · required · must be positive
  "reason": "Family vacation", // string · required · reason for the leave
  "managerId": "mgr-001"      // string · required · ID of employee's manager
}
FieldTypeRequiredValidation
leaveTypestringYesOne of: CASUAL, SICK, PRIVILEGE
startDatestringYesISO 8601 (YYYY-MM-DD); must be today or a future date
endDatestringYesISO 8601 (YYYY-MM-DD); must be equal to or after startDate
numberOfDaysintegerYesPositive integer; must not exceed the employee's available balance
reasonstringYesNon-empty string
managerIdstringYesMust reference an existing manager user ID
Success Response — 201 Created
{
  "id": "leave-abc123", // system-generated leave request ID
  "employeeId": "emp-001", // extracted from JWT
  "leaveType": "CASUAL",
  "startDate": "2026-09-01",
  "endDate": "2026-09-03",
  "numberOfDays": 3,
  "reason": "Family vacation",
  "managerId": "mgr-001",
  "status": "PENDING"
}
Error Responses
StatusWhen It OccursResponse Body
400startDate is in the past{ "error": "Cannot apply leave for past dates" }
400startDate is after endDate{ "error": "Start date must be before end date" }
400Any required field is missing{ "error": "Validation failed", "details": [...] }
401No token or invalid/expired token{ "error": "Authorization token required" }
403Token belongs to a MANAGER role user{ "error": "Insufficient permissions" }
409The requested date range overlaps an existing leave request{ "error": "Leave dates overlap with an existing request" }
422numberOfDays exceeds the employee's available balance for the requested type{ "error": "Insufficient balance", "details": { "available": 9, "requested": 50 } }

Manager Actions

Managers use these endpoints to view and act on pending leave requests from their team. Approving a leave request triggers a RabbitMQ event that decrements the employee's balance. Rejecting requires a reason. Both actions are irreversible — only PENDING requests can be processed.

Leave History

Employees can retrieve their full leave request history with support for pagination and status filtering. All responses are scoped to the requesting employee — users cannot view each other's history.

GET /leaves/my-requests Retrieve the authenticated employee's leave request history ▶
Overview
Returns a paginated list of all leave requests submitted by the authenticated employee. Supports filtering by status and controlling page size. The employee's identity is always inferred from the JWT.
Authentication
Requires Employee Token
Authorization
Employees can only view their own history. The employee ID is extracted from the JWT; no cross-user access is possible.
Request Headers
HeaderRequiredDescription
AuthorizationYesBearer <token> — must be an Employee JWT
Query Parameters (Optional)
ParameterTypeRequiredDescription
pageintegerNoPage number to return. Defaults to 1
limitintegerNoNumber of results per page. Defaults to system default (e.g. 10)
statusstringNoFilter by status: PENDING, APPROVED, or REJECTED
Success Response — 200 OK
{
  "data": [
    {
      "id": "leave-abc123",
      "leaveType": "CASUAL",
      "startDate": "2026-09-01",
      "endDate": "2026-09-03",
      "numberOfDays": 3,
      "status": "APPROVED"
    }
  ],
  "total": 5, // total number of matching records
  "page": 1, // current page number
  "limit": 10   // page size used
}

StatusWhen It OccursResponse Body

Health Checks

Health check endpoints are available on the API Gateway and directly on each individual service. The gateway health endpoint additionally reports the state of all configured circuit breakers. All health endpoints are public and require no authentication.

Overview
Returns the health status of the API Gateway along with the current state of all registered circuit breakers (CLOSED, OPEN, or HALF-OPEN) for downstream services.
Authentication
Public No token required
Authorization
None — publicly accessible diagnostic endpoint.
Request Headers
HeaderRequiredDescription
No headers required
Success Response — 200 OK
{
  "status": "ok",
  "circuits": {

}
